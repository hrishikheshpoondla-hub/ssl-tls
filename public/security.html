🤝 TLS Handshake Flow

🌐
1. Browser Connects

Browser sends a "ClientHello" to the server at port 8443, listing supported TLS versions and cipher suites.

↓
📜
2. Server Presents Certificate

Server replies with a "ServerHello" and sends its digital certificate containing its public key.

↓
✅
3. Certificate Verification

Browser checks if the certificate is trusted. For a self-signed dev certificate, the browser shows a warning (expected in development).

↓
🔑
4. Session Keys Established

Browser and server negotiate symmetric session keys. These are used to encrypt all subsequent communication.

↓
🔒
5. Encrypted Connection Active

All application data (login credentials, session cookies, responses) is now transmitted through the TLS-protected channel.

🔐 How HTTPS Protects Your Data

TLS encrypts the connection. A network interceptor sees only ciphertext — not your credentials.

Important Distinction

🔒 TLS

Protects data during network transmission between browser and server.

🔑 bcrypt

Protects passwords at rest in the database. Plaintext password is never stored.

🍪 Cookie Security Attributes

HttpOnly

Prevents JavaScript from accessing the cookie via document.cookie. Mitigates XSS attacks.

Secure

Cookie is only transmitted over HTTPS connections, never over plain HTTP.

SameSite=Strict

Cookie is not sent with cross-site requests. Mitigates CSRF attacks.

🛡️ Security Headers

Strict-Transport-Security

Tells browsers to only connect via HTTPS for the next year. Prevents downgrade attacks.

Content-Security-Policy

Restricts the sources from which the browser loads scripts, styles, and other resources. Mitigates XSS.

X-Content-Type-Options: nosniff

Prevents browsers from MIME-sniffing a response away from the declared content type.

Referrer-Policy

Controls how much referrer information is included with requests. Set to strict-origin-when-cross-origin.

⚠️ Development Certificate Notice

This project uses a self-signed certificate generated locally for development and testing. Self-signed certificates are not trusted by browsers by default, which is why you see a security warning when visiting this site. This is expected and normal in a development environment.

In a real production website, the certificate would be issued by a trusted Certificate Authority (CA) such as Let's Encrypt, DigiCert, or Comodo. The CA verifies the domain owner's identity before issuing the certificate, which causes browsers to trust it automatically.
